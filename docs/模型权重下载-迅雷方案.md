# 用迅雷下载 FreeToken 权重（替代 WSL 里的 curl）

**结论：可行，而且推荐。** 迅雷多线程 + 断点续传，拿 hf-mirror 的直链跑，
通常比在 WSL 里用 curl 死磕快 3～10 倍。原因很直接 —— 之前 curl 撞的是
Xet 存储后端的 401，而迅雷走的是纯 HTTP 分片拉取，绕开了这个坑。

---

## 一、为什么不能直接给 huggingface.co 的链接

你机器上 `C:\Windows\System32\drivers\etc\hosts` 里有一批把域名钉到
`127.0.0.1` 的条目，其中包含 `huggingface.co`。迅雷解析域名时同样读这个
hosts 文件，所以：

- 给 `huggingface.co` 的直链 → 迅雷也连不上（一样被劫持）
- 给 `hf-mirror.com` 的直链 → 正常

**所以清单里用的全是 hf-mirror.com 域名。**

---

## 二、动手前先确认三件事（在你自己的 Windows 上跑）

在 **PowerShell** 里执行：

```powershell
# 1) 确认 hf-mirror.com 没有被 hosts 劫持（没输出最好）
Select-String -Path C:\Windows\System32\drivers\etc\hosts -Pattern 'hf-mirror'

# 2) 确认 hf-mirror.com 可达（期望输出 200 或 302）
curl.exe -sIL -o NUL -w "HTTP %{http_code}`n" "https://hf-mirror.com/nvidia/Qwen3.6-35B-A3B-NVFP4/resolve/1355db6a052410cfd62085d94b58866fd0f2c3c5/config.json"

# 3) 看 D 盘剩余空间（要 ≥ 45 GB）
Get-PSDrive D | Select-Object Used,Free
```

> ⚠️ 上面第 2 条必须在你本机跑。沙箱或我这边测出来的网络结果**不能代表你的机器**，
> 这点之前已经踩过两次。

第 3 条要 45 GB 的理由：迅雷下载要占 21.85 GB，WSL 复制过去再占 21.85 GB。
复制校验通过后可以删掉 Windows 侧那副本，空间就回来了。

---

## 三、用迅雷下载

1. 新建下载任务 → **高级/批量** → 把 `freetoken_urls.txt` 里的 17 行 URL
   整个粘进去（文件里是纯 URL，没有注释，可以直接全选粘贴）。
2. 下载目录设成 **D 盘**，例如 `D:\models\Qwen3.6-35B-A3B-NVFP4`。
   > 直接下到最终位置就行（迅雷会保留正确文件名），这样第五节的整理步骤可以整段跳过。
   > 想分两步走（先下到 `D:\models\ftdl` 再整理）也可以，但没必要。
3. **别开太多并发**：把迅雷「最大同时下载任务数」调到 2～3，
   单任务线程也别拉满。hf-mirror 对同一 IP 的高并发有限制，
   开太猛容易被限速甚至 429。
4. **尽量一次下完，别搁太久。** 大分片会 302 到 `cas-bridge.xethub.hf.co`，
   那边的链接是**带时效签名**的。暂停几天再续传可能直接 403，
   得回原链接重新拿一次。

### 预期现象

三个 `model-0000X-of-00003.safetensors` 各约 9.3 / 9.3 / 3.2 GB，
是下载时间的大头。其余 14 个都是小文件（最大的 `model.safetensors.index.json`
约 13 MB）。

**文件名可能会乱。** 因为链接中途 302 跳转，跳转后的 URL 末尾不带原文件名，
迅雷可能存成一串哈希十六进制。**这是正常的，下一步会自动改回来**，
不用手工处理。

文件总数：**17 个**，合计 **21.85 GB（23,462,477,857 字节）**。

## 四、校验下载完整性（**别跳过这一步**）

**字节数对 ≠ 内容对。** 迅雷这类下载器会**预分配磁盘空间** —— 先把文件撑到
目标大小，再往里填数据。所以任务一建好，文件大小就是对的，
但内容可能还是空洞或半截。断点续传、崩溃恢复、预分配后中断，都会留下这种假完成。

```powershell
cd <仓库>   # Windows 侧克隆目录，下面两个脚本在 scripts/ 里

# 快速校验（几秒）：字节数 + safetensors 结构自洽 + 空洞采样 + JSON 合法性
python verify_model_content.py D:\models\Qwen3.6-35B-A3B-NVFP4

# 完整校验（约 20 秒~3 分钟）：再叠一层全量哈希比对
python verify_model_content.py D:\models\Qwen3.6-35B-A3B-NVFP4 --sha256
```

三层判据，一层比一层硬：

| 层 | 判据 | 能抓出什么 |
|---|---|---|
| 1 | 17 个文件的精确字节数 | 没下完、下错文件 |
| 2 | safetensors 头部自洽<br>（`8 + 头长 + 最大偏移 == 文件大小`）<br>+ 空洞采样 + JSON 合法性 | 截断、预分配空洞、下到 HTML 错误页 |
| 3 | 官方哈希全量比对 | 数据段内部的静默损坏 |

第 3 层的官方哈希取自 `/api/models/{repo}/tree/{rev}?recursive=1`，
两种算法覆盖全部 17 个文件：LFS 大文件用 `lfs.oid`（即 sha256），
其余小文件用条目 `oid`（git blob sha1，本地按 `blob <size>\0 + 内容` 复算）。

> ⚠️ 别用 resolve 直链的 `ETag` 当哈希 —— 那是 40 位 git blob sha1 且带 `W/` 弱校验前缀，
> 不是 sha256，拿来比对必然全错。也别用 `/api/models/{repo}` 的 `siblings`，
> 实测它 **不返回 lfs 字段**（17 条全是空的）。

## 五、把文件名还原（可选，通常用不上）

**如果你把迅雷的下载目录直接设成了 `D:\models\Qwen3.6-35B-A3B-NVFP4`，跳过这一节。**
文件名本来就是对的，没有东西需要还原。

只有当文件名被 302 跳转搞成哈希串时才需要整理：

```powershell
python collect_model_files.py D:\models\ftdl D:\models\Qwen3.6-35B-A3B-NVFP4
```

先预览一下会怎么改（不动任何文件）：

```powershell
python collect_model_files.py D:\models\ftdl --dry-run
```

**它靠什么认出文件？** 靠**字节数**。模型这 17 个文件的字节数互不相同，
所以「字节数 → 文件名」是唯一映射，比按文件名猜靠谱。另外两条规则：

- 文件名已经正确的，直接用名字匹配，不参与字节数猜测（防止巧合撞车）
- 临时文件、下了一半的残片、对不上的文件，**一律只报告不动它**

脚本说「全部 17 个文件就位」才算完。少了就回迅雷把没下完的任务跑完，
再重跑一次 —— 已就位的会自动跳过。

## 六、复制进 WSL

打开 WSL Ubuntu，把两个脚本拷进去：

```bash
cp <仓库>import_model_from_windows.sh ~/

# 先看看目标目录现在有什么（之前中断下载留了 12MB 残片）
ls -la ~/models/Qwen3.6-35B-A3B-NVFP4 2>/dev/null
```

导入（`--fresh` 会先清空 `~/models/Qwen3.6-35B-A3B-NVFP4`，把之前那堆残片清掉）：

```bash
bash import_model_from_windows.sh /mnt/d/models/Qwen3.6-35B-A3B-NVFP4 --fresh
```

脚本会自己做：源目录检查 → 空间检查 → 复制 → 字节数逐项校验。
复制 21.85 GB 大约 1～5 分钟，**中间看不到进度是正常的**，别以为卡死了。

校验通过、想顺手释放 D 盘那 21.85 GB：

```bash
bash import_model_from_windows.sh /mnt/d/models/Qwen3.6-35B-A3B-NVFP4 --clean-src
```

只想核对一下、不做别的：

```bash
bash import_model_from_windows.sh --verify
```

### 为什么不直接让 ft serve 读 /mnt/d

`/mnt/d` 走的是 9p 文件系统，随机读延迟比 ext4 高一个量级。
safetensors 加载要做大量 mmap 和随机读，从 9p 直接加载不只是慢，
首次启动能卡到你以为死机。**必须先复制进 ext4。**

## 七、启动

**用脚本启动**（推荐，省得记参数）：

```bash
cp scripts/serve_freetoken.sh ~/
bash ~/serve_freetoken.sh              # 加 --dry-run 只打印命令不启动
```

脚本可选参数：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只做检查并打印最终命令，不启动 |
| `--attention-backend triton` | **默认值**，零下载方案，见下节 |
| `--attention-backend fi` | 换回 flashinfer（需先装 CUDA toolkit） |
| `--skip-preflight` | 跳过 Triton 编译预检（缓存已热时省几秒） |

等价的裸命令：

```bash
source ~/freetoken-venv/bin/activate

ft serve --model ~/models/Qwen3.6-35B-A3B-NVFP4 \
  --text-model-only \
  --moe-strategy auto \
  --moe-cpu-layers auto \
  --attention-backend triton \
  --max-seq-len-override 16384 \
  --host 127.0.0.1 --port 1919 \
  --enable-cache-report
```

### attention 后端为什么默认用 triton

引擎的 `--attention-backend auto` 是按固定顺序挑的（`engine.py:127` 的注释）：

```
sm_100 → trtllm　　sm_90 + sgl_kernel → "fa,fi"　　flashinfer 可用 → fi　　否则 → triton
```

sm_120（RTX 50 系）上前两个的架构条件都不成立，于是落到 **`fi`（flashinfer）**。
而 `fi` 会在捕获 CUDA graph 时**用 nvcc 现场编译** attention 模块 —— 它要求
`CUDA_HOME` 下有 `bin/nvcc`、`include/`、`lib64`，也就是完整 CUDA toolkit。
缺了就会在「读完 22GB 权重 + 建完 banks」之后才报：

```
RuntimeError: Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist
```

**`triton` 后端不需要这些**：它的 `BackendInfo` 里没有 `requires_flashinfer`，
是纯 Triton 实现（同样用 gcc，前一步的预检已经验证过能编译）。官方在
`engine.py:210` 的报错正文里就直接推荐它：*“…or use `--attention-backend triton`”*。

代价说清楚：注意力改由 Triton 实现，单看 attention 这一步会慢一些。但本机的瓶颈是
**15/40 层专家在 CPU 上算**，注意力根本不是瓶颈，所以这个取舍基本是白拿的 ——
换来的是少一个 3~4 GB 的 CUDA toolkit 依赖。

真要换回 flashinfer：

```bash
# 1. 加 NVIDIA 的 WSL CUDA 源，装工具链（约 3~4 GB）
wget https://developer.download.nvidia.com/compute/cuda/repos/wsl-ubuntu2204/x86_64/cuda-keyring_1.1-1_all.deb
sudo dpkg -i cuda-keyring_1.1-1_all.deb && sudo apt update
sudo apt install -y cuda-toolkit-13-0      # 大版本要和 torch 的 cu13 对齐
# 2. 换后端启动
bash ~/serve_freetoken.sh --attention-backend fi
```

选 `fi` / `auto` 时脚本会先探一次 flashinfer 的 CUDA 路径，缺工具链**3 秒内**报出来，
不会让你白等一分钟。

### `--moe-cpu-layers auto` 为什么必须加

不加它，启动会在加载完权重后**报错退出**，这一步不能省：

```
ValueError: expert banks need 16.9 GiB of pinned host RAM
            but the pin budget is 11.0 GiB
```

原因是一笔账。专家权重（expert banks）要放进**锁页内存**，GPU 才能通过 PCIe
高速搬运；而 WSL 的 CUDA 走 WDDM 转发，锁页内存有配额，引擎按「物理内存 × 40%」算：

| 项 | 值 |
|---|---|
| WSL 物理内存 | 27.4 GiB |
| 引擎的锁页预算 = 27.4 × 40% | **11.0 GiB** |
| 本模型 expert banks 需要 | **16.9 GiB** |

16.9 > 11.0，装不下。`--moe-cpu-layers auto` 的做法是：把「装不下」的那部分 MoE 层
挪到 CPU 上算，它们的权重用 mlock 锁住（不占锁页配额），剩下的层继续走 GPU hybrid
（PCIe 搬运 + CPU 并行）。本机预计会挪 **14 层（0~6 与 33~39）**，日志里会明确写：

```
--moe-cpu-layers auto: banks 16.90 GiB > pin budget 11.00 GiB;
locking 14 head+tail MoE layers for CPU decode ([0, 1, 2, 3, 4, 5, 6, 33, ...39])
```

**别想着用 `FREETOKEN_PIN_BUDGET_GB` 硬抬上限绕过去。** 引擎源码注释写明：WSL 的
锁页硬顶大约是内存的一半（27.4 / 2 ≈ 13.7 GiB），而本模型要 16.9 GiB —— 抬高预算
既消不掉 CPU 层，又很可能在 `cudaHostRegister` 处直接失败。默认的 40% 是官方留的余量。

代价要说清楚：这部分层改由 CPU 计算，生成速度会比全 GPU 低。这是 8 GB 显存 +
32 GB 内存跑 35B MoE 的必然取舍，不是配置错误。

### 还有两个坑藏在后面，脚本已经帮你堵上

越过锁页预算这关之后，还会连着撞两个环境问题。两者都发生在**读完 22GB 权重之后**，
报错长得都不像环境缺失，所以单独列出来。

**坑一：缺 C 编译器（会让你误以为是 CUDA 问题）**

```
triton/runtime/build.py", line 32, in _build
RuntimeError: Failed to find C compiler. Please specify via CC environment variable
```

Triton 首次使用要把驱动辅助模块（`cuda_utils`）**JIT 编译成 .so**。内核本身有预编译
轮子可以免编译，但这个驱动模块绕不开。装：

```bash
sudo apt update && sudo apt install -y build-essential
```

只装 `gcc` 也行，但 `build-essential` 会一并带上 `libc6-dev`（标准头文件），更稳。

两个容易踩错的点：

- **它只认 PATH**。Triton 的查找顺序是 `CC` 环境变量 → `clang` → `gcc`，**不读 sysconfig**。
  如果 `CC` 被设成别的值，它会直接用那个值，不再去找 gcc。
- **不需要 CUDA toolkit**。Triton 3.6 用 `-l:libcuda.so.1` 精确链接，头文件用自己包里
  带的那份，所以那个经典的「WSL 缺 `libcuda.so` 软链」问题在这里不存在。

编译成功的 `.so` 会写进 `~/.triton/cache`，**只需成功一次**，之后启动不再编译。
脚本用一次 3 秒的预检提前暴露这个问题，省得你等一分钟才看到报错。

**坑二：`mlock` 配额不足（只警告，不阻断）**

```
WARNING  bank lock failed; leaving this and later banks pageable:
         [Errno 12] mlock(0.2 GiB): Cannot allocate memory
         (RLIMIT_MEMLOCK / `ulimit -l` caps OS-locked bytes; ...)
```

被挪到 CPU 的那 15 层，本意是用 `mlock` 锁住不让换出。但 `mlock` 受
`RLIMIT_MEMLOCK`（即 `ulimit -l`）限制，默认往往只有 8 MB，连第一个 0.2 GiB 的
bank 都锁不住。后果是这些层的权重降级为 **pageable** —— 仍然由 CPU 计算，但内存
吃紧时可能被换出，decode 会突然卡顿。

脚本的尝试顺序是：`ulimit -l unlimited` → `sudo -n prlimit`（免密可用时直接提上去）
→ 都不成就打印处理办法。Ubuntu 的**硬限通常也只有 64 MB**，非 root 提不上去，
所以要借管理员权限，二选一：

```bash
# a) 一次性：在准备敲命令的同一个终端里先执行，再重跑脚本
sudo prlimit --memlock=unlimited:unlimited --pid $$
#    $$ 是当前 shell 的 PID，脚本是它的子进程，会继承这个新配额

# b) 永久：/etc/security/limits.conf 末尾加一行，再在 Windows 侧 wsl --shutdown 重进
\1<用户名> - memlock unlimited
```

### 启动时间与就绪标志

读 22 GB 权重要 1~2 分钟，`Loading weights` 只显示到 3/3 之后还会静默一段，
这期间没有输出是正常的。

**注意：`Uvicorn running on ...` 出现得比模型加载还早，它不是就绪标志。**
后端是独立进程，服务端口先起来、模型在后台加载，中途挂掉才会补一句
`Backend worker is gone`。所以要等这两行同时出现：

```
--moe-cpu-layers auto: banks 16.93 GiB > pin budget 10.96 GiB;
  locking 15 head+tail MoE layers for CPU decode ([0, 1, ... 39])
Free memory after initialization: 0.43 GiB
```

第一行给出实际挪到 CPU 的层数（本机 15 层）。第二行是显存余量 —— **低于 0.3 GiB
就要警惕**，后面捕获 CUDA graph 可能直接 OOM。真 OOM 了按这个顺序降：

| 手段 | 效果 |
|---|---|
| 关浏览器 / WPS / 微信 | 最直接，能腾出几百 MB |
| `--memory-ratio 0.8` | 加大显存预留（代价：slot cache 变小，PCIe 命中率下降） |
| `--max-seq-len-override 8192` | KV cache 减半 |
| `--cuda-graph-max-bs 1` | 只捕获 batch=1 的图，省掉 2/4 的图内存 |

确认就绪后，另开一个 WSL 终端：

```bash
curl http://127.0.0.1:1919/v1/models
ft ctl stats     # 吞吐、延迟、VRAM、缓存池占用
ft shell         # 终端里直接聊天
```

## 八、常见问题

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 迅雷报「连接被拒绝」/ 秒失败 | hosts 把域名钉到 127.0.0.1 | 确认用的是 hf-mirror.com；查 hosts |
| 迅雷下载文件名是一串哈希 | 链接 302 跳转后丢了文件名 | 正常，跑整理脚本还原 |
| 某个大分片续传报 403 | cas-bridge 签名过期 | 删掉该任务，重新从清单粘一次链接 |
| 下载速度忽快忽慢 / 429 | 并发开太猛被限速 | 同时任务数降到 2，单任务线程减半 |
| **文件大小全对，但 `ft serve` 加载报错** | **下载器预分配的空洞没填满** | **跑 `verify_model_content.py` 见分晓** |
| 整理脚本说「源目录里一个文件都没有」 | 两个参数位置传反了 | 源目录＝迅雷下载的地方，目标目录＝整理后输出的位置 |
| 整理脚本说「未识别」 | 文件没下完，或下载目录里有别的东西 | 看它报的字节数差多少，回迅雷补下 |
| 导入脚本报「空间不足」 | WSL 的盘不够 22 GB | 清 `~/models/download.log` 等旧内容；注意天花板是宿主 D 盘 |
| `ft serve` 报 `expert banks need 16.9 GiB of pinned host RAM but the pin budget is 11.0 GiB` | WSL 的 CUDA 锁页配额（内存 × 40%）装不下专家权重 | 加 `--moe-cpu-layers auto`，见第七节 |
| 加了 `--moe-cpu-layers auto` 后报 CPU MoE executor 不支持 | 该模型的专家格式没有 CPU 路径 | 本模型是 nvfp4，**在支持列表内**；若换模型遇到再看提示 |
| 报 `Failed to find C compiler` | Triton 要 JIT 编译驱动模块，系统没装 gcc | `sudo apt install -y build-essential`，见第七节 |
| 报 `Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist` | attention 后端落到 `fi`，flashinfer 要用 nvcc 现场编译 | 加 `--attention-backend triton`（零下载），或装 `cuda-toolkit-13-0`，见第七节 |
| 报 `mlock(...): Cannot allocate memory` | `ulimit -l` 太小（默认常见 8 MB / 64 MB） | 属警告不阻断；提升办法见第七节 |
| `Backend worker is gone and cannot be restarted` | 后端进程挂了，**真正的原因在它上面几行** | 往上翻找第一条 ERROR / Traceback，别只看这一句 |
| 端口通了但请求没响应 / 随即退出 | 端口先于模型加载就绪，看起来像"起来了" | 等 `locking N head+tail MoE layers` 那行才算加载完 |
| `ft serve` 起不来 / 卡死 | 显存不够（8 GB 是最紧的一环） | 见第七节「显存余量」表格逐级降 |
| 启动速度比预期慢很多 | 15 层 MoE 在 CPU 上算 | 正常取舍。想减层数只能减显存/内存占用，见第七节说明 |
