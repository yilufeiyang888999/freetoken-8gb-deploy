## 1. 选型：为什么是这套组合

### 1.1 引擎：FreeToken

UC Berkeley / FlashML-org 出品，Apache 2.0。定位是**边缘原生 MoE 推理引擎**——把 290B+ 级前沿 MoE 压到消费级硬件上跑。核心机制是两层分层：

- GPU 显存放**非专家权重** + 一个 LRU 专家缓存；
- 完整专家池放**主机内存**；
- 每个 decode step 按**实测 PCIe/内存带宽比**把未命中专家分流到"搬到 GPU 算"和"CPU 本地算"两条路径，结果精确合并。

### 1.2 三道硬约束（决定能跑哪些模型）

| # | 约束 | 依据 |
|---|---|---|
| 1 | **必须是 MoE** | dense 模型 `--moe-strategy auto` 恒 resolve 为 `fused`，权重必须全驻显存，没有整层卸载路径 |
| 2 | **量化后权重 ≲ 24GB** | offload 家族把专家池放主机内存，27.4GB 的 WSL 要留约 3GB 给系统 |
| 3 | **专家格式须为 BF16 / NVFP4 / MXFP4** | `--moe-cpu-layers` 官方原文：*"fp8 experts cannot use it"* |

另有隐含约束：**只吃 HuggingFace safetensors，不吃 GGUF。**

### 1.3 候选对比与最终选择

| 模型 | 总量/激活 | 真实权重体积 | 32GB 内存余量 | 结论 |
|---|---|---|---|---|
| **Qwen3.6-35B-A3B-NVFP4** | 35B / 3B | **21.85 GB** | +5.5 GB | ✅ **选定** |
| Gemma-4-26B-A4B-NVFP4 | 25.2B / 3.8B | 17.53 GB | +9.9 GB | 备选 |
| gpt-oss-20b（MXFP4） | 21B / 3.6B | 12.84 GB | +14.6 GB | 冒烟测试用 |
| Muse-Glimmer-30B-NVFP4 | 30B | 21.80 GB | +5.6 GB | 备选 |

被排除的重点：Qwen3.8/3.6-27B（**dense**）、Qwen3.8-Flash-Next（有 47.7GiB PLE 表常驻主机内存，装不下）、DeepSeek-V4-Flash 284B / GLM-5.x / MiniMax-M2.5·M3（体积超限）、Qwen3-30B-A3B（官方只有 BF16 60GB，需自行量化）。

> **教训**：别凭参数规模估权重体积。最初按 35B 估了 17.5GB，实际 21.85GB，**差了 25%**——这个误差足以让内存规划全盘作废。**必须查 HF 仓库文件清单求和。**

### 1.4 平台约束

官方要求 **Linux x86_64 + NVIDIA 驱动 r580+（CUDA 13）**。Windows 走 WSL2 或桌面版。本机初始驱动 573.01 **不满足**，这是部署的第一个阻断项。

## 2. 安装：从裸机到能敲 `ft` 命令

整个安装分四层，**下层的坑不修好，上层一定失败**。顺序不能乱。

```
① Windows 宿主        驱动 r580+ / .wslconfig / WSL2 发行版
        ↓
② WSL2 Ubuntu         GPU 直通 / uv / venv
        ↓
③ FreeToken 引擎      freetoken[accel] + nightly 预编译内核
        ↓
④ 模型权重            见第 3 章
```

### 2.1 ① Windows 宿主侧

**驱动升级**（阻断项）：

```
573.01 / CUDA 12.8   →   616.92 / CUDA 13.4
显存空闲 6.2 GB      →   7.0 GB
```

**`.wslconfig`**（`C:\Users\<你的用户名>\.wslconfig`）：WSL2 默认只拿宿主内存的 50%（约 16GB），装不下 21.85GB 权重。要点：

```ini
[wsl2]
memory=28GB
swap=8GB
swapFile=D:\\<数据盘>\\wsl\\Ubuntu\\swap.vhdx
# processors 保持默认 —— MoE 的 CPU 卸载路径需要多核参与

[experimental]
autoMemoryReclaim=gradual
sparseVhd=true
guiApplications=false          # 关闭 WSLg，取回约 1GB 显存
```

> ⚠️ **踩过的坑：`swapFile` 行首不能有空格。** INI 解析会把键名读成 `" swapFile"`，该行**静默失效**——swap 仍写在 C 盘，且不报任何错。用户取消注释时很容易把缩进空格一起带进来。

**WSL2 发行版**：`wsl --install -d Ubuntu`，实体落在 D 盘（避免占用只剩 34GB 的 C 盘）。

> **顺带纠了一个认知**：机器上有 Docker Desktop，但它自带的 `docker-desktop` 发行版**没有正常用户态**，不能当开发环境用，必须补装通用发行版。

### 2.2 ② WSL2 侧（`wsl_setup_freetoken.sh`，5 步）

| 步骤 | 内容 | 实测结果 |
|---|---|---|
| 1 | 校验运行环境与架构 | Ubuntu / x86_64 / 系统 python 3.14.4 |
| 2 | 校验 GPU 直通 | RTX 5060 可见，8151 MiB，驱动 616.92 ✅ |
| 3 | 校验资源配额（内存 + 磁盘） | Mem 27.4 GB / 可用 26.6 GB |
| 4 | 安装 uv | uv 0.12.21 |
| 5 | 建 venv + 装 `freetoken[accel]` | `~/freetoken-venv`（Python 3.12），6.7 GB |

**两个环境细节值得记**：

- **系统 Python 是 3.14.4，但 venv 建在 3.12**——nightly 预编译轮子是 cp312 构建，版本必须对上。
- **脚本必须用 `$HOME` 定位 venv**。用户从 Windows 目录 `wsl -d Ubuntu` 进入时 cwd 会停在 `/mnt/d/...`，用相对路径会全盘错位。

### 2.3 ③ nightly 预编译内核（关键一步）

PyPI 版 freetoken 的 CUDA 内核要 **JIT 编译，必须有 nvcc**。官方 nightly 提供预编译内核轮子，两个加起来仅 **8MB**，免 nvcc、免 JIT。

**为什么非装不可**——不装的实测后果：

```
ft bench bw 输出（未装内核时）
format  expert    CPU-MoE   PCIe-gather  CPU/PCIe  backend
nvfp4   7.61 MB   44.4 GB/s  n/a          —         offload     ← 只能退到 offload
warning: PCIe gather bench failed ... Could not find CUDA installation.
```

装了之后：

```
format   expert     CPU-MoE   PCIe-gather  CPU/PCIe  backend
nvfp4    7.61 MB   45.3 GB/s      9.0 GB/s     5.03x  hybrid      ← 升级成功
  overlapped: CPU-MoE 46.7 + PCIe 6.1 GB/s -> hybrid fetches 11.5% of misses
```

→ **`PCIe-gather` 从 n/a 变成实数值，`auto` 才能把策略升级为 `hybrid`。** 这不是可有可无的优化，是拿到 CPU/PCIe 并行加速的前提。

**下载这个轮子本身又踩了三个坑**（详见第 3 章的网络部分）：

| 坑 | 现象 | 解法 |
|---|---|---|
| Windows hosts 劫持 | `github.com` 解析到 127.0.0.1，`Connection refused (os error 111)` | 走 GitHub 加速通道 |
| 第三方通道不可信 | 加速器在链路中间 | **强制 sha256 校验**，不匹配直接 `exit 1` |
| 本地装丢 extras | `uv pip install ./x.whl` 丢掉 `[accel]` | 用 `"freetoken[accel] @ file://..."` 写法 |

验证成功：`ft --version` → `freetoken version 0.1.3+g0d652e73a`（**构建戳出现即内核已装**）。

## 3. 模型获取：21.85 GB 权重怎么搬进来

### 3.1 两个隐藏的网络拦路虎

**拦路虎一：Windows hosts 文件劫持**

```
WSL 内诊断：
getent ahosts github.com     →  127.0.0.1     ← 关键
grep -in github /etc/hosts    →  无            ← WSL 侧干净
env | grep -i proxy          →  无
curl 直连                     →  HTTP 000，0.0039s
```

根因在 **Windows 侧** `C:\Windows\System32\drivers\etc\hosts`，里面有：

```
127.0.0.1 huggingface.co
127.0.0.1 github.com / api.github.com / raw.githubusercontent.com
...
```

**来源已确认：本机装了 Watt Toolkit（原名 Steam++），用它加速访问 GitHub。**

#### Watt Toolkit 的 Hosts 模式是三件套

| # | 动作 | 作用 |
|---|---|---|
| 1 | **改 hosts** | 把目标域名静态映射到 `127.0.0.1` |
| 2 | **本地反代** | 用 YARP.ReverseProxy 在本机起反向代理，监听 80 / 443 |
| 3 | **注入根证书** | 因为要做 HTTPS 中间人，必须自签一张证书并装入 Windows「受信任的根证书颁发机构」 |

（Watt Toolkit 在 Windows 上还有 DNS 拦截 / PAC / 系统代理三种模式可选；Hosts 是默认最常用的那个。）

#### 为什么它在 Windows 上完美工作，在 WSL 里必然失败

**Windows 侧闭环成立**：

```
浏览器请求 github.com
  → Windows 解析器先读 hosts → 拿到 127.0.0.1
  → 打到本机 443，那正是 Watt 的反代进程在监听
  → Watt 替你出海请求真 GitHub 并回传
  → 证书是 Watt 自签的，但已装进 Windows 信任库 → TLS 校验通过
```

**WSL 侧两个独立原因同时成立**：

1. **`127.0.0.1` 在两个网络命名空间里不是同一个东西。** WSL2 默认 NAT 网络模式，有**自己独立的 loopback**。Windows 的 `127.0.0.1:443` 有 Watt 在监听，WSL 的 `127.0.0.1:443` **什么都没有**。而 hosts 劫持**照样生效**——WSL 的 DNS 转发给 Windows 宿主，Windows 解析器先查自己的 hosts → `127.0.0.1` 被返回给 WSL。**结果是：地址被正确劫持了，但劫持的目的地是空的。**
2. **证书也不在。** Watt 的根证书装进了 Windows 的 `certmgr.msc`，而 WSL 信任的是 Linux 的 `/usr/local/share/ca-certificates/`。就算原因 1 解决，TLS 握手照样过不去。

> **最容易误解的一点**：在 WSL 里 `grep github /etc/hosts` **什么都查不到**——因为劫持根本没写在 WSL 的文件里，它发生在**解析链路的上游**。

#### 判据

> **`Connection refused`（秒回）= 连到了本机死端口；网络层不通是 timeout。** 实测 `curl` 返回 `HTTP 000`、耗时 **0.0039s**——3.9 毫秒本机 TCP RST 的时间，不是网络超时。**秒回这个特征一步就能把方向定死。**
> **另一个判据**：`nslookup` 绕开 hosts 直查 DNS（返回真实 IP），`getent`/应用会读 hosts——两者不一致时优先怀疑 hosts 劫持。

#### 处理策略：不处理，绕开

| 方案 | 判断 |
|---|---|
| **WSL 内走国内镜像**（`hf-mirror.com` / `gh-proxy.com`） | ✅ **采用**。WSL 侧的下载根本不碰 `github.com` / `huggingface.co`，问题自然消失 |
| 改 WSL 为 `networkingMode=mirrored` | ⚠️ 能共享 loopback，但还要把 Watt 的根证书导入 Linux 信任库，且会改变整个 WSL 的网络行为（DNS、端口映射都受影响）。**收益小于代价** |
| 在 WSL 里也装一个 Watt Toolkit | ⚠️ 有 Linux 版且机制相同（改 `/etc/hosts` + 装 CA 到 `/usr/local/share/ca-certificates/`），但没必要——镜像比它快 |
| 清理 Windows hosts | ❌ **不必动**。见下方「实测补充」 |

> **实测补充（2026-09-30 确认）**：Watt Toolkit 的 hosts 条目是**运行时写入、停止加速时还原**的。
> 本机实测：**不启动 Watt Toolkit 的加速功能，hosts 里就没有 `127.0.0.1` 条目**（WSL 侧解析即恢复正常）。
> 所以「不清理」是安全的选择 —— 代价只是别开着加速跑 WSL 下载，而 WSL 侧本来就该走镜像。
>
> **唯一要留意的例外**：卸载、崩溃、强制结束进程这类**非正常退出**时可能残留
> （官方把 hosts 条目、根证书、系统代理列为卸载后的三大残留来源）。
> 如果哪天 **Windows 本机也打不开 GitHub**，第一件事仍是查 hosts —— 但这是异常路径，非常态。

**拦路虎二：HuggingFace 的 Xet 存储后端**

```
RuntimeError: File reconstruction error: CAS Client Error:
  HTTP status client error (401 Unauthorized),
  domain: https://cas-server.xethub.hf.co/v2/reconstructions/...
```

新版 `huggingface_hub` 默认走 Xet，而 **Xet 的 CAS 服务器不受 `HF_ENDPOINT` 控制**——配了镜像照样直连官方，于是 401。

```bash
export HF_ENDPOINT=https://hf-mirror.com
export HF_HUB_DISABLE_XET=1        # ← 缺这行必 401
```

### 3.2 最终方案：迅雷 + 导入（比 WSL 内 curl 更优）

**思路**：在 Windows 用迅雷下纯 HTTP 分片，**绕开 curl 撞的 Xet CAS 401**；下完复制进 ext4。

```
hf-mirror.com 直链 → 迅雷（Windows，D 盘）→ collect/import → ~/models（ext4）
```

**四个关键设计**：

| 设计 | 原因 |
|---|---|
| **全是 `hf-mirror.com` 直链**，不给 `huggingface.co` | Windows hosts 把官方域名钉到 127.0.0.1，迅雷读同一个 hosts，一样连不上 |
| **用字节数当指纹还原文件名** | 302 跳转后文件名会变哈希串；该模型 17 个文件字节数**互不相同**，所以"字节数 → 文件名"是唯一映射 |
| **必须复制进 ext4**，不能直接读 `/mnt/d` | `/mnt/*` 走 9p 协议，随机读延迟高一个量级；safetensors 加载要做大量 mmap，会卡到以为死机 |
| 临时文件（`.td`/`.xltd`）、对不上的残片**只报告不动** | 避免误删用户文件 |

> **又一次自坑**：总字节数手算成 23,464,196,709，实际 23,462,477,857，**差 1,718,852**。逐项重算才纠正。**手算大数必复核。**

### 3.3 三层校验（终点判据）

| 层 | 内容 | 结果 |
|---|---|---|
| 1 | 17 个文件的**精确字节数** | 全对 |
| 2 | safetensors 结构自洽：`8 + 头长 + max(data_offsets) == 文件大小`，外加空洞采样（12 点 × 4KB）+ JSON 合法性 | 全对 |
| 3 | **全量 sha256 比对** | **17/17 通过**，三个分片完整哈希吻合 |

校验耗时 **19 秒读完 22GB**（≈1.15 GB/s）。tensor 名 `model.language_model.layers.N.mlp.shared_expert.up_proj.weight` 符合 Qwen3 MoE 结构。

→ **结论：权重逐字节正确，可以放心启动。**

> **校验方法上的一个发现**：`/api/models/{repo}` 的 `siblings` **不返回 lfs 字段**；要拿 hash 得用 `/api/models/{repo}/tree/{rev}?recursive=1`（带 `lfs.oid` = 内容 sha256）。而 resolve 直链响应头的 `ETag` 是 **git blob sha1**（还是 `W/` 弱校验），**不是 sha256**，拿来比对必然全错。

## 4. 专家调度：FreeToken 的技术内核

> 这一章是整个部署最核心的部分。**前四轮启动失败，本质上都是"调度资源"没算对。**

### 4.1 三道彼此独立的天花板

**这是最反直觉的一点：WSL 下有三道天花板，不是两道。**

| 天花板 | 决定什么 | 常见误判 |
|---|---|---|
| GPU 显存 | 非专家权重 + KV cache + slot cache + prefill 双缓冲 | 只盯这个 |
| 主机内存 | **所有**专家权重（expert banks）都要驻留 | 以为"总权重 < 内存"就安全 |
| **锁页内存（pinned host RAM）** | **只有需要被 PCIe 搬运的那部分 banks** | **完全没意识到它存在** |

**本机实测：模型 21.85GB < WSL 内存 27.4GB，照样启动失败。** 卡的从来不是总量，是"必须锁页的那一份"。

第三道只在 WSL 下咬人，额度是**物理内存 × 40%**：

```
27.4 GiB × 0.4 = 10.96 GiB     ← 引擎算出的 pin budget
expert banks 需要 16.93 GiB    ← 超出 5.97 GiB → 直接报错退出
```

源码机制（`engine.py::_pin_budget_bytes`）：

```
FREETOKEN_PIN_BUDGET_GB 有设    → 用它的值
非 WSL（uname 无 microsoft）    → None，即不设限
WSL                             → 物理内存 × 0.4
```

> **为什么不能靠抬环境变量绕过**：源码注释写明 WSL 的 WDDM CUDA 锁页硬顶约"内存的一半"（≈13.7 GiB），40% 是留了余量的估值。16.93 > 13.7，抬上去只会在 `cudaHostRegister` 处失败——**错误从"启动时明确报错"变成"运行中失败"，更难查。**

### 4.2 权重的两层分层结构

```
┌──────────────── GPU 显存 (8GB) ────────────────────────────────┐
│  非专家权重（attention / embed / norm / router）                │
│  + KV cache (8268 tokens → 0.16 GiB)                          │
│  + MoE slot cache（LRU 专家缓存）                              │
└────────────────────────────┬───────────────────────────────────┘
                             │ PCIe 4.0 x8   H2D 19.0 / D2H 16.5 GB/s
                             │ q* 分流：未命中专家的 11.5% 搬上来算
┌──────────────── 主机内存 (27.4GB) ─────────────────────────────┐
│  expert banks  16.93 GiB                                       │
│  ├─ GPU 层 banks → PINNED（cudaHostRegister，占 10.96 GiB 配额）│
│  └─ CPU 层 banks → LOCKED（mlock，**不占锁页配额**）            │
│       15 层：头部 [0..7] + 尾部 [33..39]                        │
│       （每层 decode 未命中率呈 U 形，两端最便宜）                │
└────────────────────────────────────────────────────────────────┘
```

> **框里那个 8268 是出厂切分值** —— KV / MoE / Mamba 三者共享同一个显存池，
> 8268 是 MoE slot cache 与 Mamba 槽分走之后剩下的"余数"，不是设计目标。
> 它同时决定了**真实可用的上下文长度**，占比与调优方法见 11.2。

### 4.3 `--moe-strategy` 四策略对比

四者共用同一套 host banks + `OffloadMoeCache`，**区别只在 decode 阶段怎么拿专家**：

| 策略 | decode 怎么拿专家 | 适用 |
|---|---|---|
| `offload` | 缺的专家走 PCIe 搬进 GPU slot cache | 显存够放 slot cache、PCIe 快 |
| `cpu` | 全在 CPU 算 | 显存极小、或有强 CPU |
| **`hybrid`** | **每层最多 fetch K 个，其余 CPU 算，两者重叠** | **PCIe/CPU 带宽比达标时 ← 本机自动选到这条** |
| `fused` | 全部专家常驻显存 | 模型放得下显存（`auto` **永不**选它） |

`auto` 的判据是 `ft bench bw` 测出的 **CPU/PCIe 倍率**，超过阈值（默认 2.0x）就升级为 `hybrid`。

### 4.4 `hybrid` 的 q\* 分流（实测数字）

```
ceilings: CPU STREAM read 69.9 | PCIe linear H2D 19.0  D2H 16.5 GB/s (threshold 2.0x)

nvfp4   7.61 MB   CPU-MoE 45.3 GB/s   PCIe-gather 9.0 GB/s   CPU/PCIe 5.03x → hybrid
  overlapped: CPU-MoE 46.7 + PCIe 6.1 GB/s -> hybrid fetches 11.5% of misses
```

解读：
- CPU 内存带宽 45.3 GB/s vs PCIe 搬运 9.0 GB/s → **比值 5.03x，远超 2.0x 阈值**；
- 于是引擎决定：未命中的专家里，**约 11.5% 搬到 GPU 算**（因为 PCIe 相对没那么慢），其余 **88.5% 留在 CPU 算**（因为 CPU 内存带宽更快）；
- 两条路径**重叠执行**——这就是所谓"带宽自适应 q\* 策略"。

> **一个未解释的差异要记下**：装内核前 PCIe H2D 是 11.1 GB/s，装后变 **19.0**（+71%）。合理猜测是首次 gather bench 失败影响了线性测量流程，但**没有证据，不要当作已解释**。

### 4.5 `--moe-cpu-layers auto`：哪 15 层该挪到 CPU

装不下锁页配额的层必须挪到 CPU 用 mlock 锁住（不占锁页配额）。算法的选择依据是**专家未命中率的分布形状**：

```
n    = min(N, ceil(N × (1 - budget / bank_bytes)))     # N = 40 层
head = (n + 1) // 2
ids  = {0 .. head-1} ∪ {N-(n-head) .. N-1}             # 头尾各一段，不取中间
```

实测计算：

```
1 - 10.96/16.93 = 0.3526
40 × 0.3526 = 14.10  →  ceil = 15 层
→ 头部 [0..7]（8 层）+ 尾部 [33..39]（7 层）= 15 层
```

**为什么挑头尾**：每层 decode 的专家未命中率**呈 U 形**——两端最便宜，挪走它们对性能损失最小。中间层命中率高，留在 GPU 收益大。

> ⚠️ **算层数必须用公式，不能用日志里四舍五入的显示值反推。**
> 日志显示 `banks 16.93 > budget 10.96`，若拿 11.0/16.9 估算得 14 层，实际是 **15 层**。
> **差一层就差 0.4 GiB 的内存规划。**

### 4.6 连带代价：prefill 变慢（这是预期行为）

触发 split residency 时，引擎会**强制关闭 `moe_prefill_overlap`** 并打日志：

```
--moe-cpu-layers split residency: disabling MoE prefill overlap
  (locked layers prefill via synchronous pageable copies)
```

原因：locked 层喂不了异步 pinned H2D 双缓冲，prefill 改走**同步 pageable 拷贝** → **长 prompt 的 prefill 会明显变慢**。

**这是设计取舍，不是故障。** 别看到日志就去调参数。

### 4.7 可行性预检（换模型前必查）

`--moe-cpu-layers` 一旦给出（`auto` 也算），引擎就**在建模前锁定 CPU decode 路径**，所以专家格式和激活函数必须都有 CPU 实现：

```
_WFMT_IDS    = {bf16, nvfp4, mxfp4_triton, ds_fp4, q4_0}          ← 含 nvfp4 ✅
_CPU_MOE_ACTS = {silu, swish, gelu, gelu_tanh, gelu_pytorch_tanh, swigluoai, swiglu_clamp}
                                                                    ← 含 silu ✅
```

本仓库两项都命中。**换模型前先查这两个名单**，不命中就只能走"抬锁页预算"那条险路。

运行时日志确认：

```
CPU MoE executor ready: threads=15 (pinned to cores 0..28)
  isa=avx2+vnni(nvfp4-w4a8) fmt=nvfp4 H=2048 I=512
  experts=256 layers=40 top_k=8 act=silu max_tokens=4
```

→ 说明 CPU 侧走的是 **AVX2 + VNNI 的 nvfp4-w4a8 内核**（利用 CPU 的 int8 点积指令做 4bit 权重解量化），不是纯标量回退。

## 5. 启动

### 5.1 启动脚本的四步编排

`serve_freetoken.sh` 把启动拆成 4 步，**按依赖顺序前置检查**——这是这份脚本最值钱的设计：

| 步骤 | 做什么 | 为什么需要 |
|---|---|---|
| **1 / 4 环境检查** | `ft` 可执行、模型目录 17 个文件、**C 编译器**、**flashinfer 解耦自检** | Triton 首次用要编译驱动模块，缺 gcc 必炸 |
| **2 / 4 内存预算体检** | WSL MemTotal×0.4 vs banks 需求、**mlock 配额**三级尝试提升、`nvidia-smi` 余量告警 | 三道天花板里最容易被忽略的两道 |
| **3 / 4 运行时预检** | 直接调 `driver.active.get_current_device()`；fi/auto 时探 flashinfer 的 `get_cuda_path()` | **把 1 分钟后的失败提前到 3 秒** |
| **4 / 4 启动** | 组装参数 → `ft serve ... \| tee 日志` | 出错时贴日志即可复盘 |

**核心思想**：FreeToken 的启动链路是**串行**的，且每步都很贵——

```
读 22GB 权重 → 建 expert banks（串行 ~45 秒）→ 算 cache 预算
  → 捕获 CUDA graph → 才第一次碰 triton / flashinfer
```

**所以任何环境缺失都伪装成"模型加载失败"，而且都在最后一分钟才炸。** 启动脚本的职责就是**用最小代价触发同一条代码路径**，让该失败的事几秒钟内失败。

### 5.2 完整启动命令与逐参数解释

```bash
ft serve \
  --model ~/models/Qwen3.6-35B-A3B-NVFP4 \
  --text-model-only \
  --moe-strategy auto \
  --moe-cpu-layers auto \
  --attention-backend triton \
  --max-seq-len-override 16384 \
  --host 127.0.0.1 --port 1919 \
  --enable-cache-report
```

| 参数 | 作用 | 为什么这么设 |
|---|---|---|
| `--model` | 唯一必需参数，其余全自动推导 | — |
| `--text-model-only` | 不建编码器塔 | 该 checkpoint 是多模态的，21.85GB **含视觉塔权重**。纯文本任务不需要，省一份显存 + 一份主机内存 |
| `--moe-strategy auto` | 交由 benchbw profile 决定 | 实测会选到 `hybrid` |
| `--moe-cpu-layers auto` | 装不下锁页配额的层挪到 CPU | **WSL 下必需**（官方原文：*"auto is for Windows/WSL only"*） |
| `--attention-backend triton` | 纯 Triton attention 实现 | **零下载，省掉 3~4GB CUDA toolkit**（详见 6.3） |
| `--max-seq-len-override 16384` | **声明**上下文上限 | ⚠️ **只改声明值，不改实际分配** —— 真上限由 KV 切分决定，出厂只有 8268（见 11.2）。32K + `memory-ratio 0.9` 同时用极可能 OOM |
| `--enable-cache-report` | 打开缓存命中率上报 | 配合 `ft ctl stats` 看真实效果 |

> **一个容易搞混的语义**：`--memory-ratio`（默认 0.9）管的是**显存**，不是主机内存。原文：*"Fraction of free VRAM the engine may use (weights + MoE cache + KV)"*。**调它救不了 host RAM 压力。**

### 5.3 启动时序：什么时候算真的好了

```
[19:49:12] Parsed arguments: ...                       ← 参数解析
[19:49:12] Uvicorn running on http://127.0.0.1:1919    ← ⚠️ 早得很，不是就绪标志！
```

## 6. 四轮故障链：完整排错记录

**共同规律：四个故障全部发生在"读完 22GB 权重之后"，全部伪装成"模型加载失败"，其中两个的报错正文一字不差但解法完全不同。**

| 轮 | 报错 | 真根因 | 解法 | 下载代价 |
|---|---|---|---|---|
| **1** | `expert banks need 16.9 GiB ... pin budget is 11.0 GiB` | WSL 锁页额度 = 内存×40% | `--moe-cpu-layers auto`（实锁 15 层） | 0 |
| **2** | `RuntimeError: Failed to find C compiler` | Triton 驱动模块 JIT 要 gcc | `apt install build-essential` | ~50MB |
| **3** | `Could not find nvcc ...`（栈在 `attention/fi.py`） | `auto` 在 sm_120 上选了 flashinfer 后端 | `--attention-backend triton` | 0 |
| **4** | **同一句报错**（栈在 `layers/activation.py`） | flashinfer 的**另一个独立调用面** | 改 `is_flashinfer_installed()` 开关 | 0 |

### 6.1 第 2 轮补充：Triton 的三个易误判点

读 triton 3.6 源码核实：

1. **只认 PATH 和 `CC` 环境变量**——查找顺序 `os.environ["CC"]` → `clang` → `gcc`，**不读 sysconfig**。若 `CC` 被设成无效值，它会直接用那个值而不回退 gcc。
2. **不需要 CUDA toolkit，也不需要 `libcuda.so` 软链**——`libraries=['libcuda.so.1']` 配 `-l:` 精确名语法，头文件用 triton 包内自带的。网上关于"WSL 要 `ln -s libcuda.so`"的老帖子**对 triton ≥3.6 已不适用**。
3. **只需成功编译一次**——产物落 `~/.triton/cache`（key = `sha256(src + platform_key())`）。修复后不必重复付代价；**换 triton 版本会让缓存失效**。

### 6.2 第 3 轮：`auto` 在 sm_120 上为什么选错

```
sm_100 → trtllm      sm_90 + sgl_kernel → "fa,fi"      flashinfer 可用 → fi      否则 → triton
```

RTX 50 系是 **sm_120**：`trtllm` 要 sm_100（cc 10.x），`fa` 要 sm_90 且需 `sgl_kernel`——**两个架构条件都不成立，于是落到 `fi`（flashinfer）**。而 `fi` 会在捕获 CUDA graph 时用 **nvcc 现场编译** attention 模块。

flashinfer 的判定（读源码核实）：需要 `CUDA_HOME` 下有 `bin/nvcc`、`include/`、`lib64`——**是完整 CUDA toolkit（约 3~4GB），不是驱动自带的运行时。**

**更优解**：`triton` 后端的 `BackendInfo` 里**没有** `requires_flashinfer`，纯 Triton 实现，自带 ptxas，只要 PATH 上有 gcc 就能编。官方在报错正文里就推荐它。

> **取舍**：attention 走 Triton 会慢一点，但本机瓶颈是 **15/40 层专家在 CPU**，attention 不是瓶颈——这笔取舍基本白拿，还省掉 3~4GB 下载。

### 6.3 第 4 轮：真正的拦路虎

**换了 attention 后端，照样炸，而且报错正文一字不差。**

```
RuntimeError: Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist
  flashinfer/jit/cpp_ext.py:61  get_cuda_path
  flashinfer/activation.py:113  silu_and_mul              ← 这次在这
  freetoken/layers/activation.py:17
  freetoken/models/qwen3_5_moe/moe.py:35   (shared_expert) ← shared_expert 的激活
  freetoken/engine/graph.py:190  _capture_graphs
```

**关键认知：attention 和 MoE experts 都已经是 triton 了，照样会在这里炸。**

因为 freetoken 的四个文件用**同一个开关**做二选一：

```python
# layers/activation.py（norm.py / rotary.py / engine/sample.py 结构相同）
if is_flashinfer_installed():
    from flashinfer import silu_and_mul                          # 走这条 → JIT → 缺 nvcc
else:
    from freetoken.kernel.triton.activation import silu_and_mul   # 纯 triton 回退
```

`is_flashinfer_installed()` 只看包能不能 import——**能 import 就判真**。而 PyTorch 的 CUDA wheel 只带运行时、不带 nvcc。

**三条路对比：**

| 方案 | 做法 | 下载 | 判定 |
|---|---|---|---|
| **改开关**（选用） | `is_flashinfer_installed()` 恒返回 `False` | **0** | 一行改动全局生效；有 triton 回退；网络差的机器首选 |
| 装 jit-cache | 版本必须与 `flashinfer-python` **严格相等** | 1GB+ | 官方正统但要联网；版本不匹配报新错 |
| 装 CUDA toolkit | `cuda-toolkit-13-0` | 3~4GB | 最重；装完首次运行仍要 JIT |

**改开关的影响面（已核实，无副作用）**：

| 文件 | 受影响算子 | 回退实现 |
|---|---|---|
| `layers/activation.py` | silu / gelu / gelu_tanh_and_mul | `kernel/triton/activation.py` |
| `layers/norm.py` | rmsnorm / gemma_rmsnorm / fused_add_rmsnorm | `kernel/triton/norm.py` |
| `layers/rotary.py` | apply_rope_with_cos_sin_cache_inplace | `kernel/triton/rope.py` |
| `engine/sample.py` | sampling | `kernel/triton/sampling.py` |

**不受影响**：attention（显式 triton）、MoE experts（triton）、b12x（本来就不会被自动选中）。这些 triton 版都是 drop-in，注释里写明 `matches flashinfer math`。

**`patch_no_flashinfer.py` 做三件事**：备份 `backend.py` → 正则定位并改写开关 → **预热 triton 版 `silu_and_mul`**（关键：避免 kernel 拖到 CUDA graph 捕获期间才首次编译）。

**回滚**：`cp backend.py.bak-flashinfer backend.py`。

> **这个补丁会随 venv 重装 / freetoken 升级丢掉**，所以启动脚本第 1 步加了"解耦自检"——每次启动查一遍，丢了当场提醒，不会等一分钟才发现。

### 6.4 排错的四条通用方法论

1. **同类报错会连续出现在不同子系统**——换后端只解决被点名的那一路。
2. **根治办法是找统一开关，而非逐个换后端。** `grep -rn flashinfer` 后看哪些 import 被 `is_flashinfer_installed()` 门控——被门控的都可安全解耦。
3. **报错位置离根因很远**——`Backend worker is gone` 是**结果**不是原因，往它上方翻。
4. **两条报错正文一样不代表同一个坑**——**看栈里的文件**：`attention/fi.py` 走换后端，`layers/*.py` 走改开关。

### 7.2 首次推理踩到的"空回答"（不是故障）

```json
{"choices":[{"index":0,"message":{"role":"assistant","content":"",
  "reasoning_content":"Here's a thinking process:\n\n1. **Analyze User Input:** ..."},
  "finish_reason":"length"}],
 "usage":{"prompt_tokens":15,"completion_tokens":128,"total_tokens":143}}
```

`content` 空、`finish_reason: length`、`reasoning_content` 一大段英文思维链——**128 个 token 全烧在思考上**，思考都没写完就被截断。

**这不是故障，是 Qwen3.6 默认开着思考模式。** 注意即使用中文提问，它也用**英文**思考。

### 7.3 关思考的正确写法（两侧都核实过）

```bash
curl -s http://127.0.0.1:1919/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen3.6-35B-A3B-NVFP4",
       "messages":[{"role":"user","content":"你好"}],
       "chat_template_kwargs":{"enable_thinking":false},
       "max_tokens":256}'
```

| 来源 | 事实 |
|---|---|
| 模型 `tokenizer_config.json` 的 chat_template | 读 **`enable_thinking`** 布尔值；`/no_think` **命中 0 次**——别按 Qwen3 老习惯去试 |
| freetoken `server/api_models.py` | `ChatCompletionRequest` 直接收 `chat_template_kwargs`；内部 `THINKING_OFF_KWARGS = {"enable_thinking": False, "thinking_mode": "disabled"}` **一次广播**，模板只认自己认识的那个 |

**什么时候该关**：

| 场景 | 建议 |
|---|---|
| **ChatBI / 结构化抽取 / 工具调用 / RAG 问答** | **关**——否则每轮先烧几百 token，延迟翻倍、答案还可能被截断 |
| 复杂推理 / 代码 / 数学 | 保留，但 `max_tokens` 给到 ≥2048 |

`finish_reason` 是最快的判据：`length` = 预算不够（思考吃掉了），`stop` = 正常结束。

```bash
ft shell              # 终端里直接聊天
```

**建立基线（可复现）**：用工作区的 `bench_tok_s.py` 测一次，才有调优的参照物 —— 否则改了参数不知道是变好还是变坏。

```bash
~/freetoken-venv/bin/python \
  tools/bench_tok_s.py
```

**本机实测结果**（RTX 5060 Laptop 8GB + 15/40 层 CPU，2026-09-30）：

| 指标 | 实测值 | 读法 |
|---|---|---|
| 端到端吞吐 | **23.75 tok/s**（5 次中位数） | 含首 token 延迟，等于**用户感知速度** |
| 纯 decode 速度 | **27.80 tok/s** | 排除 TTFT，等于**引擎真实吞吐（天花板）** |
| TTFT（首 token 延迟） | **1.64 s** | 仅占总耗时 **15%** |
| 首次预热 | **11.21 s**（服务已热）/ **40.17 s**（首次部署后） | kernel 编译 + 专家首次换入，**只有第一次付** |

**怎么判断够不够用**：对照两条体感阈值 —— 对话式问答（RAG QA）约 **5 tok/s** 起，ChatBI 出表格 / JSON 建议 **10 tok/s** 起。**23.75 tok/s 是 ChatBI 阈值的 2.4 倍**，结论：**这套配置足以支撑 RAG / ChatBI 的 POC，不需要再调优**。

**瓶颈在哪（这决定了优化方向）**：

```
端到端 23.75  ← 含 1.64 s TTFT
纯 decode 27.80  ← 引擎天花板
差 17%（4.05 tok/s）→ TTFT 只占 15% → 瓶颈是 decode 本身，不是首 token
```

**提速的三个旋钮**（按代价从低到高）：

| 顺序 | 手段 | 预期收益 | 代价 |
|---|---|---|---|
| 1 | 关浏览器 / WPS / 微信，腾显存给 slot cache | 小幅（显存余量仅 0.66 GiB） | 无 |
| 2 | `ft ctl cache --moe N` 运行中调专家缓存池 | 中（直接减 PCIe 拉取） | 无（不重启） |
| 3 | 减少 CPU 层数 | **通常为负收益** | 见下 |

> ⚠️ **第 3 条基本不用试**。CPU 层数由 `--moe-cpu-layers auto` 按锁页预算算出（15 层），减层 = 更多专家被迫走 PCIe —— 而当前选 `hybrid` 恰恰因为 **CPU/PCIe 带宽比 5.03x**，CPU 本地算明显更划算。减层是把便宜路径换成贵路径。
>
> **更重要的判断：27.80 tok/s 的纯 decode 已远超 POC 需求（阈值 10 tok/s），继续调优的边际收益很低。** 把时间花在 RAG 链路 / ChatBI 提示词上，回报率高得多。

## 8. 运维手册

### 8.1 日常启动

```bash
# WSL 里
sudo prlimit --memlock=unlimited:unlimited --pid $$   # 让 15 层真正锁住（可选）
bash ~/serve_freetoken.sh                             # 前台启动，日志 tee 到 ~/models/freetoken-serve.log
#   ↑ 脚本会在服务就绪后自动把 KV 切分调到 16384（见 11.2）；不想要就加 --kv-context 0
```

### 8.2 显存不足的降压顺序

`Free memory after initialization` 低于 0.3 GiB 就要按序降：

| 手段 | 代价 |
|---|---|
| 关浏览器 / WPS / 微信 | 无 |
| `--memory-ratio 0.8` | slot cache 变小，PCIe 命中率下降 |
| `--kv-context 8192` | 上下文减半，腾出约 0.16 GiB（**别用 `--max-seq-len-override` 顶替 —— 它只改声明值，不动实际分配**） |
| `--cuda-graph-max-bs 1` | 丢掉 batch 2/4 的图，高并发时回退非图路径 |

### 8.3 mlock 配额（能跑但会卡）

```
WARNING bank lock failed; leaving this and later banks pageable:
  [Errno 12] mlock(0.2 GiB): Cannot allocate memory (RLIMIT_MEMLOCK)
WARNING --moe-cpu-layers: layers [...] settled pageable instead of OS-locked
```

**不阻断启动，但别忽略。** 降级为 pageable 后仍由 CPU 计算，只是内存吃紧时会被换出 → **decode 突发卡顿**。

根因是 `RLIMIT_MEMLOCK`（Ubuntu 默认常见 64 MB，连第一个 0.2 GiB 的 bank 都锁不住）：

```bash
ulimit -l unlimited                                    # 硬限允许时
sudo prlimit --memlock=unlimited:unlimited --pid $$    # 硬限挡着时，在父 shell 里执行
# 或 /etc/security/limits.conf 加： <用户名> - memlock unlimited  →  然后 wsl --shutdown
```

### 8.4 重启 / 回滚 / 重装后

| 场景 | 动作 |
|---|---|
| 重启服务 | `Ctrl+C` 或 `ft down`，再 `bash ~/serve_freetoken.sh` |
| 重装 venv / 升级 freetoken | **必须重跑** `python /mnt/c/.../patch_no_flashinfer.py`（启动脚本会自检并提醒） |
| 想恢复 flashinfer | `cp backend.py.bak-flashinfer backend.py` |
| 脚本改动后 | **工作区源文件 ≠ `~/` 副本**，改完要重新 `cp` 到 `~` |

> ⚠️ **脚本版本分叉问题**：工作区（`/mnt/c/...`）与 `~/` 各有一份，改完必须 `cp`。**这个坑在部署过程中出现过多次**——用户跑的常常是旧版，输出对新不上。相对地，Python 脚本可以直接跑 `/mnt/c/...` 路径，绕开这个问题。

## 9. 接入编程 IDE

### 9.1 先看服务对外提供什么

FreeToken 一次注册了**三套协议**（`api_server.py:421-424`），这决定了你能接哪些工具：

| 协议 | 端点 | 典型客户端 |
|---|---|---|
| **OpenAI Chat Completions** | `POST /v1/chat/completions`、`GET /v1/models` | Cline、Roo Code、绝大多数 VS Code 扩展 |
| **Anthropic Messages** | `POST /v1/messages`、`POST /v1/messages/count_tokens` | Claude Code（含 VS Code 扩展） |
| OpenAI Responses | `POST /v1/responses` | Codex CLI |

外加控制面：`GET /v1/stats`、`GET /v1/requests`、`GET /v1/cache/status`。

**三套都能用**，所以选客户端的余地比想象中大。

### 9.2 选哪个扩展（先说一个坑）

| 扩展 | 状态 | 评价 |
|---|---|---|
| **Cline** | 活跃维护 | **首选**。开源、BYOK、OpenAI Compatible 支持完整 |
| **Roo Code** | 活跃维护 | Cline 的 fork，配置项更多，二选一即可 |
| ~~Continue~~ | ⛔ **已停运** | 2026-06 被 Cursor 收购，`v2.0.0` 是最后一版，仓库已只读。**网上大量教程仍在推荐它** —— 不要用它开新项目 |

> **别按搜索结果里的教程配置**：Continue 相关的文章（包括不少大厂文档）都还没更新，照做会装到一个不再维护的扩展上。

### 9.3 ⚠️ 必须知道的三个约束

**约束一：上下文上限取决于 KV 切分 —— 填错必炸，这是最容易踩的坑**

Cline / Roo Code 每次请求都会带上：系统提示 + 当前文件内容 + 工具定义 + 对话历史。**轻松突破 8268**。

**前提**：服务端 KV 池必须先调到 16384（见 11.2）。**没调的话 prompt 超过 8268 直接 HTTP 400**，
而且报错发生在对话中途，很容易被误判成扩展本身的毛病。

| 服务端 KV 切分 | `Context Window Size` 该填 |
|---|---|
| **16384**（`serve_freetoken.sh` 默认会自动调） | **16384** |
| 8268（出厂值，或传了 `--kv-context 0`） | **8192** |

先确认真实值，别猜：

```bash
curl -s http://127.0.0.1:1919/v1/cache/status \
  | python3 -c "import json,sys;print('KV =', json.load(sys.stdin)['geometry']['num_pages'])"
```

而它们的 **Model Configuration 里有 `Context Window Size` 字段，默认值往往按 128000 算**（厂商通用默认）。如果你不改，扩展会以为有 12.8 万 token 可用，把文件全塞进去 → 请求直接超限失败。

**所以配置时必须显式改这两个字段**：

| 字段 | 值 |
|---|---|
| Context Window Size | **16384**（KV 未调优时填 8192） |
| Max Output Tokens | **2048**（给思考/长回答留余量；配合关思考可调小） |

**约束二：关思考传不进去 —— 这是 IDE 接入的真正难点**

Qwen3.6 默认先输出思维链。而「关思考」这个开关**只能放在请求体里**：

| 写法 | 适用协议 | 说明 |
|---|---|---|
| `chat_template_kwargs: {"enable_thinking": false}` | 三套通用 | 最直白，属模板私有参数 |
| **`thinking: {"type": "disabled"}`** | OpenAI + Anthropic | **协议标准字段，推荐** |
| `reasoning_effort: "none"` 或 `"off"` | OpenAI | 等价写法（`model_meta.py:90`） |

依据：`openai_api.py:48-70`、`anthropic_api.py:297-301`、`model_meta.py:89-90`。

**问题在于**：Cline / Roo Code 的 OpenAI Compatible 配置**只有 `Base URL` / `API Key` / `Model ID` 三个输入框**，没有自定义请求体的入口。所以思考会一直开着 —— 每个请求先烧几百 token，在 16384 的窗口里这是灾难性的。

**解法：加一层网关**（见 9.5），由它统一注入。这也是第 10 章网页端用的同一个组件。

**约束三：别把代码补全（autocomplete）指向它**

- 本机实测 23.75 tok/s，而补全是**每次打字停顿就触发**，延迟完全无法接受
- 这个模型没做过 FIM（fill-in-the-middle）训练，补全质量本来就差

补全请另配一个小模型（Ollama 跑 `qwen2.5-coder:1.5b` 之类）。**把 Cline 的补全功能关掉**，只用它做对话 / agent 任务。

### 9.4 方案 A：直连（最简，但思考全开）

适合「先跑通」或「就想看模型思考过程」。

```
Base URL   http://127.0.0.1:1919/v1
API Key    随便填（本地服务不校验）
Model ID   Qwen3.6-35B-A3B-NVFP4
```

⚠️ 前提：服务要允许跨源 —— 但 IDE 扩展是**服务端发起请求**，不走浏览器，**不受 CORS 限制**。所以直连无需任何额外配置。

代价：**思考关不掉**。每个请求先思考，慢且吃上下文。

### 9.5 方案 B：走网关（推荐）

`ft_gateway.py` 会替你注入关思考字段，IDE 侧无感：

```bash

# 终端 2：网关

```

然后把扩展指向网关：

```

API Key    随便填

```

**网关做的事**：

| 行为 | 说明 |
|---|---|
| 注入 `thinking: {"type":"disabled"}` | 客户端没表态时才注入；**已表态的尊重原样**（想临时开思考，客户端自己传 `thinking: {"type":"enabled"}` 即可覆盖） |
| 按协议选字段 | `/v1/responses` 用 `reasoning: {"effort":"none"}`，其余用 `thinking` |
| 同时托管网页 | 浏览器打开 `http://127.0.0.1:1950/` 即聊天界面（**同源，无 CORS 问题**） |
| 不注入时用 | `--keep-thinking` 原样转发 |

省事的话抄这份 **Cline 配置**（VS Code 里 `Ctrl+,` → 搜 roo/cline，或直接在扩展面板填）：

```
Max Output Tokens     2048
```

**Roo Code 额外一步**：它的 OpenAI Compatible provider 有 `openAiCustomModelInfo`，需一并设
`{"contextWindow": 16384, "maxTokens": 2048, "supportsImages": false}`。

### 10.1 交付物

**`chat.html`** —— 单文件聊天界面，零依赖、零构建，原生 `fetch` + SSE 流式渲染。

### 10.2 两种打开方式

**方式一（推荐）：走网关，同源无 CORS**

```bash
python3 tools/ft_gateway.py
# 浏览器打开 http://127.0.0.1:1950/
```

网关同时托管页面和转发 API，**同源**，浏览器不会触发任何跨源检查。页面顶部会显示 `服务 http://127.0.0.1:1950/v1 · Qwen3.6-35B-A3B-NVFP4`。

**方式二：直接双击 `chat.html`**

```

```

此时页面以 `file://` 打开，会去请求 `http://127.0.0.1:1919/v1`（跨源）。**必须让服务放开 CORS**：

```bash
bash ~/serve_freetoken.sh            # 脚本已默认传 --cors-origins '*'
```

若看到控制台报 `blocked by CORS policy`，说明服务是用旧脚本启动的（没带这个参数）——重新 `cp` 脚本并重启即可。

### 10.3 为什么需要 `--cors-origins`

服务默认的跨源白名单是**硬编码的三个 Tauri 桌面端 origin**（`args.py:68`）：

```
tauri://localhost, http://tauri.localhost, http://localhost:1420
```

普通网页不在其中，请求会被浏览器拦掉。`args.py:774` 提供了 `--cors-origins`，`api_server.py:412` 的规则是：

```python
allow_origins = ["*"] if "*" in origins else origins
```

即 **传 `'*'` 就展开为允许任意来源**。

| 取值 | 行为 | 何时用 |
|---|---|---|
| `'*'`（脚本默认） | 放行任意来源 | 浏览器直开网页。**服务只监听 127.0.0.1，不对局域网开放**，风险可控 |
| `'http://127.0.0.1:8080,...'` | 精确白名单 | 你想收紧时 |
| `''`（空串） | **完全关掉 CORS 中间件** | 只用 curl / IDE 时 |

```bash
bash ~/serve_freetoken.sh --cors-origins 'http://localhost:8080'   # 自定义
bash ~/serve_freetoken.sh --cors-origins ''                        # 关掉
```

> 注意空串与「不传」是两种行为：空串 = 无 CORS 中间件；不传 = 保留 Tauri 默认白名单。脚本会原样透传。

### 10.4 用起来

| 操作 | 说明 |
|---|---|
| 输入框回车 | 发送（`Shift+Enter` 换行） |
| 「关闭思考」勾选框 | 默认**勾上**。发结构化请求时保持；想看推理过程就取消 |
| 底部统计行 | `TTFT 1.64 s · 总耗时 10.8 s · 约 23.8 tok/s` —— 每次回答后实时算，用来感知负载 |
| 「清空」 | 重置对话历史（历史在内存里，刷新页面也会清空） |

**排查**：

| 现象 | 原因 / 对策 |
|---|---|
| 顶部显示「未连接」 | 服务没起，或端口不对。WSL 里 `ft ctl stats` 确认 |
| 控制台 `blocked by CORS policy` | 见 10.3，用 `--cors-origins '*'` 重启服务 |
| 页面 404 / 显示「找不到聊天页面」 | 走网关时 `chat.html` 不在 `ft_gateway.py` 同目录，用 `--html <路径>` 指定 |
| 回答很长但内容为空 | 思考吃光了 `max_tokens` —— 勾上「关闭思考」（见 7.3） |
| 启动报 `Address already in use` | 多半是撞上 `ft serve` **自己的内部端口**，见 10.5 |

### 10.5 网关启动报 `Address already in use`

```
OSError: [Errno 98] Address already in use
```

**含义**：这个端口上已经有进程在监听。和 `TIME_WAIT` 无关 ——
`HTTPServer` 默认开了 `SO_REUSEADDR`，`TIME_WAIT` 拦不住它；能报这个错，
就是**真有进程占着**。

#### 头号原因：撞上 `ft serve` 自己的内部端口

**实测**：`ft serve` 起来后，除了主端口 `1919`，**它还会占住紧邻的一个端口
（`1919 + 1`）** —— 那是 supervisor 与 backend worker 之间的内部通道。
kill 掉占这个端口的进程，`ft serve` 会因为 worker 丢失
（`Backend worker is gone`）而**整体退出** —— 这也正是启动脚本会跟着停的原因。

所以 **网关不能用 1920**。早期把默认端口设成 1920 是个设计错误，
**现在默认值已改为 `1950`**（离上游 1919 拉开 31 个端口，避开 `1919 + N` 的扫描区）。

自查（一条命令看清上游到底占了哪些）：

```bash
ss -lntp | grep -E ':19[12][0-9]'
```

若 `1919` 和紧邻端口属于同一个 python3 进程树，就是这种情况 —— **不用杀**，
换端口即可（默认值已避开）。

#### 其他原因

| # | 原因 | 说明 |
|---|---|---|
| 1 | 上一次的网关还在跑 | 开在另一个 WSL 窗口里忘了关，或又开了一个终端重复启动 |
| 2 | **按的是 `Ctrl+Z` 而不是 `Ctrl+C`** | `Ctrl+Z` 只是**挂起**（SIGTSTP），进程还在、端口照占。`fg` 能拉回前台；`Ctrl+C` 才是退出 |
| 3 | 当初用了 `&` / `nohup` 丢后台 | 关掉窗口也不会退 |

#### 处置

```bash
# 1) 看是谁占的（ft_gateway.py 启动失败时已替你打印 PID 和命令行）
ss -lntp | grep -E ':19(19|20)'

# 2) 是残留的旧网关 → 停掉它；是 ft serve 的内部端口 → 别杀，换端口（见下）
pkill -f ft_gateway.py                 # 或精确一点：kill <PID>

# 3) 重新启动（默认 1950，已避开）
python3 tools/ft_gateway.py
```

**换端口**（默认值已避开，只在自定义时才需要）：

```bash
python3 tools/ft_gateway.py --port 1960
```

聊天页面**不用改** —— `chat.html` 请求的是同源地址（`location.origin + "/v1"`），
自动跟随网关端口。只有 IDE 里的 Base URL 要跟着改。

> 脚本还会在「网关端口离上游不到 20」时打印一行警告 —— 贴着 `1919` 就是自找冲突。

#### 网关会自己诊断

绑不上时它会先扫 `/proc/net/tcp` 拿 LISTEN socket 的 inode，再去
`/proc/<pid>/fd` 反查进程，直接打印占用者 PID 和命令行，不再甩 traceback。
平台差异也顺手抹平了：

> **Windows 上的坑**：`HTTPServer` 会设 `SO_REUSEADDR`，而 Windows 的
> `SO_REUSEADDR` 语义是「**允许两个 socket 绑同一个 addr:port**」（Linux 只对
> `TIME_WAIT` 放行）。所以在 Windows 上端口冲突**会静默通过** —— 两个进程都
> "启动成功"，谁先绑的谁收流量，另一个永远收不到请求还不报错。脚本因此改用
> **不带 `SO_REUSEADDR` 的裸 socket 做预检**，两个平台判据才一致。
> （WSL 是 Linux 语义，本来就会正常报错。）

## 11. 16K 上下文到底够不够 —— 适用边界

> 起因：接进 VS Code 后，让它读一篇长一点的文档就不够了 —— **那这台机器还有什么意义？**

### 11.1 先把 16384 翻译成人话

| 计量 | 大约等于 |
|---|---|
| 英文 | 约 1.1 万词 / 6 万字符 |
| 中文 | 约 1.5~2.5 万字 ≈ **一份 20~30 页的技术文档** |
| 代码 | 约 1200~1800 行（含注释） |

**能装下什么**：一份中等篇幅的技术方案、一篇论文、一个中型源文件、一整轮带检索的问答。
**装不下什么**：200 页的产品手册、一整个代码仓库、长对话历史 + 长文件同时在线。

> ⚠️ **上面这张表的前提是先调过 KV 切分。** 出厂状态下真上限只有 **8268**（约为上表的一半），
> 超过直接 HTTP 400 —— 这是全篇最容易踩的坑，机制与解法见 11.2。

### 11.2 真相：真上限是 8268，不是 16384（以及怎么调回来）

#### 声明值和实际值不一致，以小的为准

启动日志：

```
Allocating 8268 tokens for KV cache, K + V = 0.16 GiB
```

而 `/v1/models` 会说 `max_model_len: 16384`。**这两个数不一致**，实测：

```
HTTP 400  {"error":{"message":"prompt is too long: 8911 tokens > 8268 ...
```

**8268 是硬上限**，超过直接 400，且**不会自动扩容**（`num_pages` 全程不变、
`last_rebuild` 保持 `null`）。`/v1/models` 报的 16384 只是**模型架构声明**，
不代表本机真的分配了那么多。

> 这一个坑足够解释"为什么 16K 还是不够用" —— **实际连 8K 都不到**。

#### 为什么恰好是 8268：三块共享一个池子

`/v1/cache/status` 能读到完整几何：

| 用途 | 出厂值 | 单位成本 | 占用 | 占比 |
|---|---|---|---|---|
| KV pages | 8268 token | 20 480 B/token | 0.158 GiB | 4.5% |
| MoE slot cache | 1108 专家 | 1 775 616 B/专家 | 1.832 GiB | 52.5% |
| Mamba slots | 24 槽 | 64 389 120 B/槽 | 1.439 GiB | 41.2% |
| **合计** | | | **3.429 GiB** | 100% |

三者**共享同一个显存池**，预算约束为：

```
可用(KV + MoE) = 总池 − mamba槽数 × 每槽字节
```

**交叉验证**（`limits` 里三个 `max` 恰好等于"整个池只给这一种资源"）：

| 除法 | 结果 | `limits` 声明 |
|---|---|---|
| 总池 ÷ kv_per_token | 182 932 | `kv_tokens.max = 182932` ✓ |
| 总池 ÷ moe_per_expert | 2 110 | `moe_experts.max = 2109` ✓ |
| 总池 ÷ mamba_per_slot | 58.2 | `mamba_slots.max = 58` ✓ |

三个全中，共享池模型成立。**8268 不是设计目标，是"余数"** ——
出厂切分 `mamba 24 + MoE 1108` 先把 1.99 GiB 吃掉，剩下的才轮到 KV。

#### 要长上下文，从 Mamba 割让

| 资源 | 管什么 | 能不能让位 |
|---|---|---|
| Mamba slot | **并发序列上限**（每个活动请求占一个） | **能** —— 24 路并发对单用户是纯浪费 |
| MoE cache | decode 速度（常驻专家数） | 已饱和，实测 1108→1290 **无提速** |
| KV pages | **上下文容量** | 本次要加的就是它 |

#### 实测：调到 16384，零速度代价

```bash
# 运行时重建 —— 服务空闲时 1~6 秒完成
curl -s -X POST http://127.0.0.1:1919/v1/cache/rebuild \
  -H 'Content-Type: application/json' \
  -d '{"num_pages":16384,"moe_cache_size":1108,"num_mamba_slots":20,"mode":"if_idle","timeout":280}'
```

| 配置 | 15 826 token 的 prompt | 端到端 tok/s | 纯 decode tok/s |
|---|---|---|---|
| KV 8268 / mamba 24（出厂） | ❌ 400（8 911 就拒） | 21.5 | 25.9 |
| **KV 16384 / mamba 20** | ✅ 通过 | 21.7 | 26.0 |

**代价：并发上限 24 → 20，单用户无感。速度无可测变化。**

> 顺带否掉一条弯路：把 Mamba 压到下限（16）去换更多 MoE（1108 → 1290）
> **一点没快** —— 说明 1108 已饱和，瓶颈不在专家命中率。别再折腾这块。

> 记一次测量教训：中途测到过 17.4 tok/s，一度以为调 KV 有 19% 代价。
> 做 A/B/A 复测后，A 组（KV 16384）回到 21.66，与 B 组（KV 8268）21.51 重合 ——
> **那次异常是前面连发两个 16K prefill 干扰了测量**。
> 单次 bench 的噪声可达 ±15%，**几何调整这类结论必须做交叉复测**。

#### 怎么固化

运行时调整**重启即失效** —— 启动参数里的 `--max-seq-len-override` 只改声明值。
两条路：

```bash
# ① 启动脚本已内置（默认开启，改完记得同步到 ~/）
bash ~/serve_freetoken.sh                  # 服务就绪后自动调到 16384
bash ~/serve_freetoken.sh --kv-context 0   # 不要这项

# ② 独立工具，随时可查可调
python3 ft_cache_tune.py                             # 只看现状 + 建议（不动服务）
python3 ft_cache_tune.py --context 16384             # 按目标上下文调
python3 ft_cache_tune.py --context 16384 --dry-run   # 只算不提交
python3 ft_cache_tune.py --restore                   # 回出厂切分
```

**两道安全闸**：服务忙时返回 `status: busy` 直接放弃；超预算时 `status: rejected`
并**保留旧配置继续服务**。都不会把服务搞挂。

### 11.3 为什么在 VS Code 里"感觉特别不够"

**不是文档长的锅，是 agent 框架的开销。** Cline / Roo Code 这类扩展：

1. 每轮请求都带**系统提示词 + 全部工具定义**（固定开销，几千 token 起）
2. 每读一个文件、每次 grep、每个 diff，**都追加进对话历史**
3. 它们默认按 **128000** 规划上下文（我们已强制改成 16384 防爆）

也就是说：**agent 的架构假设就是"云端 128K 大窗口"**。把 16K 的本地模型塞进这个框架，
它按 128K 的方式用，三四个回合就见底。**16K + agent 框架 = 天生不匹配**，
这不是调参能弥补的，差着一个数量级。

### 11.4 场景适配表

| 场景 | 输入量级 | 16K 够吗 | 结论 |
|---|---|---|---|
| 单文件问答、解释报错 | 2~8K | ✅ | 本地强项 |
| 单据 / 发票结构化抽取 | 1~3K | ✅ | 本地强项 |
| ChatBI 自然语言问数 | 3~10K | ✅ | 本地强项 |
| RAG 知识库问答（检索后） | 3~8K | ✅ | **长文档的正确解法** |
| 整篇长文档一次性理解 | 32K+ | ❌ | 走 RAG，或上云端 |
| Cline / Roo agent 多轮改代码 | 64~128K | ❌ | 本地做不了，别指望 |
| 长对话 + 长文件同时在上下文 | 持续增长 | ❌ | 需要 128K 级窗口 |

### 11.5 长文档的正解是 RAG，不是长窗口

这是本项目的核心判断，也是能直接讲给客户的一句话：

> **文档变长，不该靠"把窗口撑大"来解决，该靠"检索把范围缩小"。**

```
11 万字的产品手册
  ├─ 长窗口方案：把 11 万字（≈15 万 token）全塞进去 → 本地装不下，云端成本高、延迟大
  └─ RAG 方案：切块 → 检索 top-3~5 块（3~8K token）→ 16K 窗口绰绰有余
```

RAG 还顺带躲开长窗口的两个隐性坑：

| 坑 | 说明 |
|---|---|
| **Lost in the middle** | 上下文塞满时，模型对**中间段**的召回率明显下降 —— "塞进去了"不等于"读懂了" |
| 成本与延迟 | 输入 token 越多，首 token 越慢、费用越高 |

（企业 RAG 知识库做过 50+ 文档、检索准确率 95%+，这条路径本来就在手上。）

### 11.6 分工建议

| 任务类型 | 放哪 | 理由 |
|---|---|---|
| 客户 ERP 数据 / 发票 / 合同解析 | **本地** | 数据不出内网，这是硬性要求 |
| 批量结构化抽取（几百上千张单据） | **本地** | 零 token 成本，可通宵跑 |
| RAG 问答（检索层 + 生成层） | **本地** | 输入受控在 8K 内 |
| 整篇长文档理解 | RAG / 云端 | 见 11.5 |
| agent 多轮改代码 | 云端 128K | 本地窗口差一个数量级 |

### 11.7 一句话定位

**16K 不是缺陷，是定位。**

- 作为 **私有化 POC 演示机 + 敏感数据处理器**：**够用，而且正中靶心**（RAG / 抽取 / ChatBI 全在 16K 内）
- 作为 **个人写代码的 agent 主力**：**不要指望** —— 16K 窗口 + 23 tok/s，撑不起来
- 作为 **AIGC 工程能力的训练场**：**很值** —— 部署链路、显存预算、容器化、网关、多协议接入
  已经完整跑通一遍，这套经验本身可复用

> ⚠️ 别指望换台式机的 P100 16GB 来救 —— P100 是 **Pascal（sm_60）** 架构，
> 跑不了 NVFP4 量化，也不支持 bf16 原生。要长窗口得换 sm_90 及以上的大显存卡。

### D.1　WSLg 显存收益怎么验证

**关键前提：配置写了 ≠ 生效。** `.wslconfig` 只在 WSL 启动时读取，改完必须 `wsl --shutdown` 才生效。

```
⚠️ wsl --shutdown 会杀掉正在跑的 ft serve。先做完 tok/s 实测再重启。
```

验证三步（在 WSL 里跑）：

```bash
# ① 确认 WSLg 当前是否在运行
ls -d /mnt/wslg 2>/dev/null && echo "WSLg 在运行" || echo "WSLg 未运行"
ps aux | grep -iE 'weston|xwayland' | grep -v grep

# ② 看显卡上挂着谁的进程（关键：找 Xwayland / Weston）
nvidia-smi

# ③ 空闲基线：不跑任何 GPU 程序时的显存占用
nvidia-smi --query-gpu=memory.used,memory.free --format=csv,noheader
```

**判读方式**：

| 状态 | 期望结果 |
|---|---|
| 关闭前（WSLg 在跑） | `nvidia-smi` 进程表里能看到 **Xwayland**，占用约 **1233 MiB** |
| 关闭后（重启 WSL 且空闲） | 进程表里**没有** Xwayland / Weston；显存占用基线**下降约 1.2 GB** |
| `/mnt/wslg` 仍存在 | 说明配置未生效 —— 没执行 `wsl --shutdown`，或配置文件路径不对 |

> **注意**：对比必须让 **ft serve 处于停止状态**，否则它自己占 6~7 GB，把 1.2 GB 的差异淹没了。
> 正确顺序是「停服务 → 测基线 → 改配置 → `wsl --shutdown` → 重进 → 再测基线」。

### D.2　真实 tok/s 怎么测

已交付 **`bench_tok_s.py`**（工作区根目录，纯标准库，零依赖）：

```bash
~/freetoken-venv/bin/python \
  tools/bench_tok_s.py
# 加 --thinking 可额外测一组「带思考」的对照
```

**脚本刻意做对的三件事**：

| 设计 | 原因 |
|---|---|
| **第 1 次请求丢弃** | CUDA graph 捕获、kernel 首次编译、专家换入都在那一次，耗时是稳态的几十倍。不预热测的是"冷启动时间" |
| **强制关思考** | 否则 token 全烧在思维链上，测出的不是推理速度，也与你 ChatBI 场景的真实负载不符 |
| **两个口径分开报** | 端到端 tok/s（含首 token 延迟，用户感知）vs 流式纯 decode 速度（引擎真实吞吐）。**差距大 = 首 token 延迟高**，这是"15/40 层专家在 CPU"的典型特征 |

输出会给出 5 次的中位数、TTFT、纯 decode 速度，以及读数参照（对话式问答约 5 tok/s 起、ChatBI 建议 10 tok/s 起）。

**实测结果（2026-09-30，完整一次）：**

固定负载：输入 41 tok（"从 1 数到 200"），`max_tokens=256`，关思考，`temperature=0`。

| 指标 | 实测值 | 占比 / 读法 |
|---|---|---|
| **端到端吞吐** | **23.75 tok/s**（5 次中位数） | 含首 token 延迟 = **用户感知速度** |
| **纯 decode 速度** | **27.80 tok/s** | 排除 TTFT = **引擎真实吞吐（天花板）** |
| **TTFT（首 token 延迟）** | **1.64 s** | 仅占总耗时 10.81 s 的 **15%** |
| 首次请求预热（服务已热） | **11.21 s** | 仅第一次付 |
| 输入 / 输出 | 41 tok / 256 tok（**打满**，`finish_reason=length`） | 输出干净，不混自然收尾 |

**5 次逐次明细**（全部打满 256 tok）：

```
第 1 次： 10.86 s │ 23.58 tok/s │ length
第 2 次： 10.73 s │ 23.86 tok/s │ length
第 3 次： 10.79 s │ 23.73 tok/s │ length
第 4 次： 10.60 s │ 24.15 tok/s │ length
第 5 次： 10.78 s │ 23.75 tok/s │ length
```

**三个结论**：

1. **够用，且有 2 倍以上余量。** 23.75 tok/s 是 ChatBI 阈值（10 tok/s）的 **2.4 倍**、RAG QA 阈值（5 tok/s）的 **4.7 倍**。这套 8GB 消费卡 + 15/40 层 CPU offload 的取舍站得住。

2. **瓶颈是 decode 本身，不是首 token 延迟。** TTFT 只占 15%，端到端与纯 decode 只差 17%（脚本 30% 阈值判"接近"）—— **优化 TTFT 收益极小**。要提速只能动 decode 路径（见 7.4 的三个旋钮）。

3. **方差极小（极差 0.57 tok/s）= 系统稳定。** 这说明 `--moe-cpu-layers` 那 15 层即使降级 pageable（见 8.3），在实际负载下**没有被换出**（内存余量足够），无需为它焦虑。

> **预热时间的两种口径**：本次 **11.21 s** 是服务已运行一段时的首请求；首次部署后（Triton 编译缓存为空）实测为 **40.17 s**。差异来自 kernel 编译缓存 `~/.triton/cache` 是否已建立，**都只付一次**。
